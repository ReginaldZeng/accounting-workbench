## 一、为什么要改

**现状问题一：菜单层几乎没有权限架构。** 三级菜单里真正设了准入门槛的只有 3 个（系统设置、月结核对、仓库类型），其余全部——银行对账、对账程序、理财对账、资金看板、账户台账、科目余额表、物流对账、物流计提、付款对账、凭证归档、月结看板——**任何人登录进核算工作台都能看见、都能点进去**。真正的管控全压在动作层（上传/取数/认领/封存/录入）。即"门大开、柜子上锁"。一级菜单完全没有权限概念。

**现状问题二：三套分类法并存打架。**

| 分类法 | 分组 | 用在哪 |
|---|---|---|
| 业务性质 | 月结与结账 / 报表与台账 / 常规对账 / 其它小工具 / 通用 | 侧栏菜单 |
| 工具线 | 银行对账 / 物流计提 / 成本台账 / 凭证归档 / 系统设置 | 账号管理页的权限点分组 |
| 岗位 | 成本岗 / 应收岗 / 总账岗 / 资金岗 / 财务经理 | 模块上的装饰标签（不判权） |

管理员配权限时看到的分组，和侧栏看到的分组对不上号，得自己在脑子里翻译一遍。

**现状问题三：设置页只能建二级，建不了三级。** 建模块的接口不收 `parent` 参数（app.py:870），自建的永远是二级。一级不是实体、只是从模块 `grp` 字段反推出来的字符串，因此改不了名、排不了序、组一空就消失。顺序完全靠代码里数组的先后。内置工具的分组写死在代码里。

### D12 展开：现状已正确，此前的「bypass 隐患」是误报

初稿曾提示「侧栏按 `role === 'admin'` 放行，不区分主/分级管理员，会让准入点对分级管理员形同虚设」。**经核实此提示错误，特此更正：**

- `is_super(user)` 的定义就是 `role == 'admin'`（db.py:308），两者是同一个东西。
- 分级管理员＝ `role='normal'` + `manage_accounting` 权限点做出来的（UserAdmin 建号时 role 固定 `normal`），**不满足 `role === 'admin'`**。

所以侧栏（Sidebar.jsx:47）与后端全权发放（app.py:348）**本来就只放行主管理员**，分级管理员一直是照准入点走的。**无绕过口子，无需改代码。**

**且收紧不会把分级管理员关在门外**：账号管理不在工作台侧栏里，它挂在门户上（Portal.jsx:268），准入走 `can_admin`／`isAdmin` 身份，与核算工作台的准入点完全无关。分级管理员进核算工作台侧栏是空的（那本来就不是他的活），他的本职——在门户上管本组账号——照常跑。要用工具，主管理员单独给他开准入点即可。

### D11 展开：为什么必须先做 key 化

岗位名单本来就存在 DB（`nav_posts` 设置项，主管理员在设置页可增删，上限 20），**不是写死在代码里的，名字随时能改**。

但现在是**拿名字当主键**：把"成本岗"改成"成本会计"，实际动作是"删掉成本岗 + 新建成本会计"，而挂在模块上的"成本岗"会被读取时的名单过滤静默丢弃（app.py:817）。今天只是掉个装饰标签，不痛；**岗位一旦升级成模板、账号又要绑岗位，改一次名就会把模板绑定和账号绑定一起弄丢**。

改成 key 化之后：`{key: "cost_acc", label: "成本会计"}`，label 随便改，模板和账号绑的是 key，绑定跟着走。

### D3 展开：为什么准入点要自动生成

菜单树一旦能自建，马上有个问题：**自建出来的菜单，权限点从哪来？** 总不能每加一个三级菜单就改一次代码。

所以把两类权限彻底分开：

- **准入点（能不能进这个菜单）＝ 跟着菜单树自动生成。** 在设置页建一个「BOM报价审核」，系统自动就有「进入 BOM报价审核」这个权限点，账号管理页立刻能勾。不用改代码。
- **动作点（进去能干什么）＝ 仍由代码持有（CAP_META）。** 上传、取数、封存、一键录入金蝶这些是代码里的真实行为，必须代码定义。自建的空占位页没有动作，自然也不需要动作点。

**"敏感点代码定死、默认不给、只能单向加严"这条铁律纹丝不动**——敏感的全在动作点这边，自动生成的准入点一律非敏感。

### D4 展开：为什么岗位不做权限机制

1. **导航根本不需要岗位来驱动。** 每个菜单都有准入点后，"能进的才显示"这条规则本身就实现了"每个人看到自己那份导航"——成本会计手上只有成本模块那几个准入点，侧栏自然只剩成本模块。中间不需要岗位这一层。
2. **岗位判权会引入第二套判权逻辑，和已有规矩打架。** 例："成本会计"模板里要不要含"取数/上传（会覆盖全员数据）"这个敏感点？含了就绕过地板；不含，模板也没省下多少事。
3. **规模用不上。** 8 个岗位、十几个人。角色模板那套是给几百人、高流动性组织用的。
4. **"财务经理是岗位还是层级"的歧义自动消失。** 按人给权限，不用先给它归类。

## 六、存量账号迁移（D5：全部不给）

**做法：** 新增的 21 个准入点，存量账号一个都不补。上线后由主管理员按人开——**实操上就是给每个人选一次岗位、一键套用**，岗位模板正好当迁移工具使。

**必须知道的后果：**

1. **上线瞬间，普通账号的侧栏是空的**，直到管理员给他配好。所以配置动作要么在上线前做完，要么和上线放在同一个操作窗口里，不能拖。
2. **主管理员不会被锁死**——侧栏判定 `role === 'admin'` 直接放行所有 cap（Sidebar.jsx:47），主管理员照常看得见全部菜单。
3. **分级管理员照准入点走，不受影响、也无绕过口子。** 他 `role='normal'`，不满足上面那条放行；本职工作（在门户上管本组账号）不经过工作台侧栏，照常跑。详见 D12。

**回滚：** 若上线后发现配置来不及，把这 21 个准入点临时并入启动时的自动补齐名单，即可恢复成"人人可见"的今天状态，不丢数据。

## 七、工作量与分期

**这一笔（本确认书范围）：**

1. 菜单树数据驱动（一级实体化、支持 parent 建三级、order 排序、内置位置可覆盖）
2. 第三种节点类型（可进入 + 有子项）+ 侧栏三处交互改造
3. 准入点自动生成 + 账号管理页自动渲染
4. 菜单树按新结构落地（含 3 处改名、1 处内容上提、9 个新占位）

## 十、账号页三栏化（V2.53 · 2026-07-17）

**背景**：本次加了 22 个菜单准入点后，账号管理页把「准入点」和「动作点」两套东西平铺在一起、还各用一套词汇（准入点按业务板块、动作点按工具线），管理员看到「进入 对账程序」和「上传资金流水」得自己在脑子里连线；且有挂错的（「上传科目余额表」挂在银行对账下，可科目余额已搬去报表模块）。业务方要求按「先能不能进去、再进去能干什么」重构。

**已实现**（样机见同目录 `账号页三栏样机_方案B改_第3栏只出进得去的_20260717.png`，业务方选定此形态）：

- 每个工作台内分**三栏**：① 块头两个开关＝能不能进工作台；② 准入点＝看得见哪些菜单（按业务板块）；③ 动作点＝进去能干什么。
- **第③栏只显示第②栏勾了的菜单的动作**，按菜单归堆并标出处（如「上传科目余额表」归到「科目余额 · 报表模块」）。进不去的菜单，其动作根本不渲染——矛盾组合从「能勾但不该勾」变成「压根不存在」。
- **取消某菜单准入 → 它底下已授的动作权限跟着一起收回**（业务方定）。前端即时同步、后端 `_cascade_revoke` 强制兜底（直接调接口也绕不过），杜绝「屏幕上看不见却仍然授予」的幽灵权限。

**新增字段**（后端 `CAP_META_STATIC`，纯展示、独立于 `kind`）：`tier`（nav 准入点 / act 动作点）、`mod`（该动作归哪个菜单 key）。**为什么不复用 `kind`**：`kind` 驱动 `default_perms` 的默认给不给，动它会连带改掉 BP 存量账号的默认板块，故另开字段只管账号页怎么摆。同时把 14 个动作点的归属菜单一一标注，顺带**修正了「上传科目余额表」「月结看板·封存本期」的历史挂错位置**。

**端到端验证**：第②栏板块顺序与侧栏一致 ✓；第③栏只出进得去的菜单、按菜单归堆 ✓；取消准入→动作整堆消失、勾回→堆回来但内部为空（不自动还权）✓；绕过前端直接调接口硬塞动作点→后端强制收回 ✓；BP 动作点认到自己板块门控 ✓。

**顺带发现（记录，非本次范围）**：一键套用岗位模板只给菜单准入点，不含「进入工作台」总闸（总闸是 `kind=enter`，不在模板的 secs/mods 范围）。真实核算组账号建号时 `default_perms` 已给总闸，故无影响；但若某账号总闸缺失，套模板会出现「给了一堆菜单准入却整个工作台进不去」。若要更稳，可让套用逻辑连带补上本工作台的 enter 总闸。

### 准入点增减（第四节清单的增量）

### 一处必须跟着改的：`subject_upload` 的归属菜单

`subject_upload`（上传科目余额表）原 `mod="sbal"`。**`sbal` 撤下后不能不管**：`mod` 指向菜单树里不存在的 key 时，`_caps_for_ui` 算不出 `gate`，该动作会掉进账号页第③栏的「不受菜单门控」堆里**恒显示**——变成一条谁都看得见、却对不上任何菜单的幽灵权限，正是第十节三栏化要根治的那类问题。

已改为 `mod="rptdash"`。选择「改指」而非「删除」，是因为手工上传金蝶报表做人眼核对是业务方明确要保的能力，报表仪表盘正是它的新家；`rptdash` 现为「敬请期待」、无人持有 `enter:rptdash`，故这条动作眼下对所有人都不渲染，等页面建好即自动接上。

## 一、为什么要做

**法务两个人，一个月一百份合同。** 人均每月 50 份、每天两三份，还得干别的活。这不是"要不要提效"的问题，是扛不住。

**为什么是这个做法，不是做个上传页面。** 靠人主动打开工具、主动传合同的工具，命运基本是：上线、培训、用两周、没人再点。因为它给人**加了一步**。本方案挂在钉钉审批流上，**人零动作**——审批人打开钉钉，该关注的地方已经标好了。

**时间窗是这件事最大的技术优势。** 合同审批要走好几天，AI 有几十小时。多数 AI 产品只能跑一遍（用户在等），跑一遍就必然会编。我们可以用时间换准确度（见 D5）。

## 二、定位：这个工具是什么，不是什么

**这一节比后面所有功能都重要。定位错了，功能做得再好也会被弃用。**

| 是 | 不是 |
|---|---|
| **预审** —— 在人来看之前，把该关注的地方标出来 | **审查** —— 不出结论、不做判断 |
| 法务和财务的**阅读索引** | 可直接转给业务部门的**意见书** |
| 帮人省掉"通读一遍找可疑条款"的**体力活** | 替人做决定 |

**四条铁律：**

1. **只标不判。** 措辞一律是"以下条款建议关注"，不是"存在风险"。
2. **每条必须带原文引用。** 让人一眼能对。对不上的意见，比没有意见更糟。
3. **读不了就明说。** 加密件、格式异常、一期的扫描件——就在评论里回"本合同未做预审"并说明原因。**绝不假装审了。** 审批人可以接受"这次没帮上忙"，不能接受"以为帮了其实没帮"。
4. **版本必须对齐。** 合同重新提交＝重新预审，意见上标明"本次预审基于第 N 版"。
5. **靠不住就降级。** 二期扫描件走 OCR 之后，意见必须挂免责声明（见 D16）。**不可靠的意见必须自己承认不可靠**，这是第 3 条的延伸。

### D2 展开：为什么不给 11 个人各配一个数字分身

初版设想是财务部 11 人每人配一个数字员工。**否决，理由是社交风险，不是技术。**

一块屏、11 个工位、跟部门花名册一一对应、每天统计每人的分身省下多少工时——这个画面在职场里只有一种读法：**"这是在算我们几个人能被替掉。"** 这工具能不能活，取决于同事愿不愿意用它。这块屏可能一天之内把信任烧光。

且有实际问题：**那 10 个分身没活干**（只有合同预审有触发器），画面会是一个人在忙、十个人发呆——"AI 摸鱼办公室"。

**按活分之后三个问题同时消失：** 墙上那间办公室不再是花名册，是**成绩单**（显示干掉了几件苦活，不是有几个人）；每件活自带触发器和队列，不会空转（空转说明这件活本来就不该自动化，自己就看出来了）；不用凑 11 份提示词，有几件活就几个工位。

**附带好处：这间办公室会自己长大。** 一期两张桌子，半年后三张，一年后五张——每多一个小人，都是真的多干成了一件事。它自己就是这个部门的进度条，而且是最诚实的那种，因为空转的工位藏不住。

### D10 展开：大屏的泄漏风险

大屏挂在办公室电视上，**路过的每个人都能看见**。如果气泡上写着"正在读《XX 公司采购合同》"，全公司路过的人都知道你们正在跟 XX 公司签合同——还在谈判的供应商、还没公告的合作、正在比价的两家。金额条款不用露，**光是对方名字就可能是敏感信息**。

**做法：** 大屏气泡只写类型 + 进度——"正在预审一份采购合同（第 3 章／共 8 章）"。反正没人真的读那个气泡，他们看的是数字牌。**真实合同名只在点进工位、且有权限时可见。**

这条必须在上线前定死。上线了再改，等于已经漏过一轮。

### D15 展开：为什么提示词不抄开源角色库

参考过 `agency-agents-zh` 的 `legal-contract-reviewer.md`。**结论：结构可参考，内容必须自己写。**

它就是一段结构化的中文——身份、四步流程、输出一张风险表。它的框架省了我们想结构的时间，这个价值是有的。但**它不知道你们公司真正在意什么**：哪些付款节点踩过坑、哪类发票出过事、哪个结算周期吃过亏。这些只有财务经理和法务经理知道。

**D8（关注点切开）的具体清单，就是这两份提示词的核心，也是本确认书最重要的两个待确认项（Q3／Q4）。**

### D16 展开：OCR 会废掉两遍法——所以扫描件必须降级

**这是本工具最隐蔽的一个坑，必须记录在案。**

D5 那个"第二遍回原文核对"之所以能抓住 AI 瞎编，前提是**原文可靠**。扫描件不是：OCR 出来的文本自带错字，而合同里错一个字要命——"不得转让"识别成"不转让"、金额 `1,800,000` 识别成 `1,300,000`、"甲方"识别成"乙方"。

**致命之处在于此时两遍法查不出来。** 两遍读的是**同一份 OCR 文本**，AI 引用得一字不差、核对完美通过——但那份"原文"本身就是错的。**这道防线在扫描件上静默失效**，不会有任何告警。随后法务点开原件一看是张图，AI 引用的文字对不上，工具信任当场归零。

**所以扫描件的意见不能与电子版同等对待，三条硬规矩：**

1. **意见必须挂免责声明**："本份为扫描件识别，文字可能有误，请以原件为准。"
2. **OCR 置信度低的段落直接跳过，不标。** 宁可漏，不可错。
3. **大屏与列表上，扫描件必须有醒目标记**，让法务一眼知道这份的意见要打折看。

**成本不是障碍：** 服务器已在腾讯云，腾讯云自带通用文字识别，100 份／月 × 几十页，量级约每月百元。上线前核当期价格。

**为什么排二期（而非难度原因）：** 一期先用电子版证明**法务真的要这个东西**。若法务看完电子版意见的反应是"写的都是废话、我还得自己重看一遍"，那 OCR 就是白做的功能。**先证明有人要，再扩覆盖面。** 且 Q2 尚未摸底——万一扫描件只占两成，一期上 OCR 就是为 20% 的量，去冒污染另外 80% 可信度的风险。

**二期启动条件：** 一期验收通过 + Q2 摸底完成。

## 四、一期范围

**做：**

1. 钉钉审批事件订阅 + 附件下载（腾讯云公网可达，已确认）
2. 财务预审员 → 法务预审员，串行，两遍法
3. 意见贴回钉钉审批评论
4. 处理列表（含全量留痕）
5. 只读大屏（单工位特写 + 战绩牌）

**不做：**

- 扫描件 OCR（**已定要做，排二期**——见 D16。一期遇到扫描件明说不审）
- 可点击走进去的完整办公室、多工位远景、移交动画
- 财务／法务之外的任何角色

**战绩牌长这样**（大屏的主角）：

> 今天预审 **7** 份 · 标出 **23** 条待关注 · 为法务省下约 **2.3** 小时
> 本月累计 **86** 份 · **31.5** 小时

小人和办公室是**衬托**，让数字牌看起来是活的。动画的新鲜感撑不过一周，**能让人一直抬头看的是数字在涨**——涨到年底就是这个工具存在的理由，不用写 PPT，它自己每天在墙上写。

## 五、待确认问题

### 卡开发的：**1 个**

**Q1（法务经理签字）：所有走钉钉审批的合同，一律自动、全量、无人工确认地发送至 DeepSeek 云端 API 做预审。确认可行吗？**

**这一条不签，后面全部不做。**

必须原样这么问，不能简化成"我们想做个合同预审工具"。**这不是"法务想用时手动传一份"，是全量自动外发**——没有人点"确认发送"，没有人筛选，合同进了审批流就已经出公司了。性质完全不同。

**参考事实（供判断）：**
- 工作台已在腾讯云公网服务器上，公司对"业务数据放在公网服务器"本就接受。**本条要争取的只是再往前一步：交给第三方 AI 服务商。** 腾讯云是我们租的机器、数据归我们管；DeepSeek 是把数据交给别人。这确实是新的一步，但范围比听起来窄。
- 需向法务出示 DeepSeek 服务条款中的两条：**API 数据是否用于模型训练（有无关闭开关、默认状态）**、**留存多久**。**签署前截图存档。**

**若答复是"脱敏后可以"**：需追问"具体脱哪些"。合同脱敏基本做不到——金额脱了没法审付款条款，公司名脱了没法查主体资质，条款原文本身就是敏感内容。

### 不卡开发的：

- **Q2：扫描件占比多少？** 翻 20 份历史审批数一下。**OCR 已定要做（D16），所以这个数不再决定"上不上"，而是决定两件事：** ① 二期何时启动、优先级排多高；② 一期上线时要不要同步改规定要求业务传电子版——**能改规定就先改，比任何技术都便宜，而且它把问题消灭掉而不是补救**。
- **Q3（财务经理写）：财务预审员标哪些条款？** 粗线条是"钱怎么走"：付款节点、结算周期、发票义务、税率与开票类型、预付比例。**需具体到可执行的颗粒度**，不能是"重要条款"。
- **Q4（法务经理写）：法务预审员标哪些条款？** 粗线条是"出事了怎么办"：主体资质、违约责任、知识产权、保密、争议解决、解除条件。同样需具体。
- **Q5：Q3 与 Q4 有无重叠？** 需两人对一遍。重叠＝同一件事说两遍＝噪音（见 D8）。
- **Q6：一期支持哪些合同类型？** 采购／服务／租赁／其他。建议占比最大的那类先做。
- **Q7：留痕谁能看？** 大屏只显示脱敏信息，点进工位看真实合同——这个准入点给谁。
- **Q8：预审失败了通知谁？** 是静默记录，还是钉钉推给某个人。
- **Q9：大屏挂哪？** 财务办公室、法务办公室，还是都挂。总监独立办公室要不要一块。

## 七、工作量与分期

**这一笔（本确认书范围）：**

1. 钉钉企业应用（建应用、开审批读权限、配事件订阅回调、验签）
2. 附件下载（钉盘）+ 格式识别 + 按条款切片
3. 两遍法调用链（提取 → 回原文核对 → 丢弃对不上的）
4. 贴回钉钉审批评论 + 版本标注
5. 处理列表 + 全量留痕
6. 只读大屏（单工位特写 + 战绩牌 + 脱敏）

**依赖（非开发）：**

- 钉钉主管理员配合建应用与授权（**已有路子，业务方确认**）
- 腾讯云公网回调地址（**已具备**）
- Q1 法务签字（**卡开发**）
- Q3／Q4 两份提示词（业务方编写，可与开发并行）

**第二笔（另立项）：**

- **扫描件 OCR（已定要做，D16）**——启动条件：一期验收通过 + Q2 摸底完成。含腾讯云 OCR 接入、置信度阈值、免责声明、降级标记
- 完整办公室（多工位、移交动画、可点击进入）——**等工位凑够三个以上再做**。数据结构一期已按 D12 预留，届时是纯前端工作，后端不动

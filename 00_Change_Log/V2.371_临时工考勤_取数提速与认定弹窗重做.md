## 一、取数：357 秒 → 143 秒

**默认改成只取「报了工时的日子前后各一天」。**

判定要用的都是有上报的那些日子——「打卡撑不起上报」「报了工时却没打卡」都只发生在这些天。
整月全取多出来的，只有「◇有打卡·未计工时」这个**明确写着「不是问题」**的中性档。

2026-06 实测（同一份汇总表，两种取法各跑一次，逐项对）：

| 指标 | 整月 | 只取上报日±1 |
|---|---|---|
| ⚠ 打卡撑不起上报 | 4 | **4** ✓ |
| ⚠ 报了工时没打卡 | 0 | **0** ✓ |
| ✓ 打卡撑得住 | 1,594 | **1,594** ✓ |
| ◇ 白夜混合 | 0 | **0** ✓ |
| ◇ 有打卡·未计工时 | 1,252 | 1,242（少 10，预期） |
| **用时** | **311 秒** | **143 秒** |

**红灯一条不差。** 页面上有「取整月每一天」的勾选，需要完整中性档时勾上；
生成的打卡表在「考勤组」列写明 `钉钉取数·仅上报日±1天`，下载下来不会误以为漏了数据。

⚠ **前后各一天不能省**：夜班的下班卡落在次日，只取上报当天算不出在厂时长——
先试过只取当天，2026-06 凭空多出 188 条假「撑不起上报」（4 → 192）。

并发档位 4 → **6**（实测 30.8 → 37.5 次/秒，退避重试兜住限流，零失败）。

## 走过的弯路，记下来别再试

试过用 `listschedule` 预筛「这一天谁有打卡」，只对名单内的人日取数。
**没用，反而更慢（401 秒 vs 357 秒）**：它列的是当天**有排班**的人，
固定班组的人不打卡也有排班条目，8,550 条只筛掉 650 条，却先花了约 1,800 次去问。
已写进代码注释。

Description: 【报表导出】序时簿百万行改造——孝感星期九（107）2026 年 9 期几百万行序时簿
             连续两次导出失败的根治：① 每 100 万数据行自动分表页（序时账簿 / 序时账簿_2 …），
             绕开 Excel 单表 1,048,576 行硬上限；② 取数不再整本攒内存排序，分页直写临时
             SQLite + 索引排序 + 流式读出直写 Excel，内存恒定。排序口径逐行不变。

## 背景

用户导 2026 年 9 期，107 孝感市星期九序时簿几百万行，连续两次失败。8 期同一主体
42.3 万行时 V2.613 已修过一轮（翻页提速 + 只写模式），但那次只解决「翻页慢」和「写 Excel
时单元格对象爆内存」，没解决「整本先攒进内存 list 排序」——量再上一个数量级就顶穿。

## 查实

- **Excel 单表硬上限 1,048,576 行**：`report_export.py` `_write_journal` 永远写单个
  「序时账簿」表页，无行数防护；几百万行时 openpyxl 必抛错——与「每次必败」吻合。
- **内存**：`kingdee_client.py` `fetch_journal_full` 把整本攒进内存 list 再本地排序
  （排序口径「凭证号+分录行号+内码」必须在取完后排——V2.613 为翻页提速把服务端排序
  改成了按内码 keyset）。每行约 1KB Python 对象开销，几百万行 = 几个 G，
  服务器总共 3.6G，MemoryError 或整机 OOM 杀进程。
- 取数翻页本身已是 keyset 分页（每页 5000 行、恒定 1~2 秒），不是瓶颈，不动。

## 改法

**取数侧（`kingdee_client.py`）**：`fetch_journal_full` 替换为两个函数——
`journal_to_temp()`（翻页逻辑/字段/on_page 回调全沿用，每页 5000 行 executemany 进临时
SQLite，取完建索引，返回库路径+总行数；异常路径也删库）与 `iter_journal_temp()`
（按索引 ORDER BY 流式产出 14 列，游标懒加载不占内存；生成器关闭即释放连接，
之后才能删库文件）。排序键拆列存（`_sort_num` 的 `(0,数字)/(1,文本)` 拆成 flag/num/str
三列），`ORDER BY flag,num,str,…` 与 Python 元组序逐项等价（flag 先分胜负，同 flag 内
另一列全 NULL 由有效列定序，永不跨类型比较）。

**写盘侧（`report_export.py`）**：`_write_journal` 改接迭代器+总行数，每写满
`JOURNAL_SHEET_MAX=1,000,000` 行新开表页（序时账簿 / 序时账簿_2 / …），各页独立表头、
冻结 A2、自动筛选、列宽；总行数取数结束时已知，各页筛选范围在写行前精确设置（只写模式
要求）。`export_one` 串起「journal_to_temp → iter_journal_temp → build_workbook → 存盘」，
finally 里关生成器+删临时库（取消/异常同路径）。进度（取序时账簿 xx 万行 / 写入 Excel
n/total）与取消（回调抛 _Canceled）语义不变。

**文案（`routers/rptexport.py`）**：回执邮件补一句「序时账簿超过 100 万行时自动分表页」。

## 上线注意

- 推 main 后服务器自动部署并重启后端——**正在跑的导出会被中断**，发布避开导出窗口，
  重启后重导即可（已导好的文件不受影响）。
- 临时库约每百万行 200~400MB，落系统临时目录（/tmp），几百万行约 1GB；若服务器 /tmp
  不足会在该主体 errors 里见到写库报错（不静默），届时再把临时目录挪到落地目录旁。
- 真机回归建议：先重导 2026 年 8 期 107（42.3 万行，已有旧文件可逐行对照），再跑 9 期全量。

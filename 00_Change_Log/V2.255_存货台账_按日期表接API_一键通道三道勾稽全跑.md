**【存货台账】按日期表接 API，🅰 通道三道勾稽全跑**。

**起因**：业务方看第①步页面时问「存货收发存汇总表（跨维度）这个是不是不用手工上传了」。查证后发现**两件事**：

1. 那张跨维度表 🅰 通道取的就是它（`HS_INOUTSTOCKSUMMARYRPT`），上传纯属冗余——这一点 V2.115/V2.116 起就成立，只是页面文案没说清。
2. **更重要的是我此前答错过一次**：曾说「两表互勾只能走🅱上传」。实际不是技术限制——`RPT_INOUT_BYDATE`(`HS_INOUTSTOCKSUMMARYBYDATERPT`) 这个 formid 自 V2.53 起就定义在 `kingdee_client.py` 里，**但从来没有取数函数**，勾稽①的第二张表一直只能从上传的工作簿里拆。业务方 2026-08-10 提供的官方接口文档表明这张表同样走 `GetSysReportData`。**是没做，不是做不了。**

**改法**：

1. 新增 `kc.fetch_inventory_bydate(year, period, org)`。⚠**Model 与跨维度表不同**：本表**有** `FBEGINDATE`/`FENDDATE`/`FPeriodStartDate`（跨维度表没有——以前给跨维度表发这三个纯属多余，靠金蝶忽略才没炸），`FCOMBOTotalType`(汇总依据) 与 `FDimType`(显示维度) 皆为必填。剔小计/总计行仍用【库存状态为空】判据（V2.115）。
   **只取四个金额列**（期初/收入/发出/结存）——这张表在本工具里唯一用途就是互相验证合计；多取列既慢，又会诱使别处误用它当明细（明细以跨维度表为准，那张才带仓库维度）。
2. `analyze-kingdee` 路由补取该表并喂给内核。**失败不拦取数**：勾稽①缺席时内核照旧只跑后两道，前端单独显示 `bd_msg` 说明缺的是哪一道——不与科目余额的 `gl_msg` 混在一起，否则会让人误以为只是账实勾稽出了问题。
3. 页面文案改准：🅰 块由"取回三样"改为"**取回四样**"并列出按日期表、标明"三道勾稽全跑"；🅱 块补一句"**这张表 🅰 也能自动取，日常不必上传**"，并把该通道的存在理由收敛为两条——拿原表逐行核对、以及含货损/盘盈亏页时做损益归集。

**验证**（真金蝶只读，107 / 2026-5）：

| 项 | 结果 |
|---|---|
| 按日期表取数 | 2,770 行（与跨维度表同行数） |
| 勾稽①两表互勾 | 期初 12,645,632.27／收入 24,222,127.26／发出 25,909,708.27／结存 10,958,051.26，**四项差额全 0** |
| 走真实 `analyze-kingdee` 路由 | `ties` 三项齐全 `['self_balance','two_reports','book_vs_actual']`、`credible=True`、`bd_msg` 为空 |
| 回归 | 内核单测 17/17 绿；`import app` OK；前端打包通过 |

**结论：🅰 与 🅱 现在是有实证的能力等价**（不是 V2.117 那种宣称完又破裂的），唯一差别是**损益归集**——货损/盘盈亏两页是成本会计在底稿里手工加的，金蝶报表接口没有这个东西，不管怎么改都得人工提供。

**遗留**：

- 🅱 通道**建议保留**，但理由已变：不再是"正式月结必须走它"，而是①拿原件逐行核对（业务方定过"系统取数要留 API + 手工上传双模式，怕领导觉得是黑箱"）②损益归集。
- 确认书 v1.2 §2「数据源主从」与 Q2 的表述需同步（原文写"按日期表仅🅱上传时做勾稽①"）。

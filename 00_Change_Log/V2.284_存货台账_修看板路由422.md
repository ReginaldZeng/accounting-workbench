**【存货台账/看板】修看板接口 422**。

**现象**：业务方在服务器上打开存货看板，报
`取数失败：/api/cost-ledger/dashboard?year=2026&period=5&org=107&months=5&basis=current 422`。

**根因（我引入的）**：V2.281 加 `basis` 开关时，把新 helper `_dash_from_store(y, p, org)`
**插在了 `@router.get("/api/cost-ledger/dashboard")` 与 `def cost_ledger_dashboard(...)` 之间**。
装饰器只认紧跟其后的那个 def——于是路由绑到了 helper 上，它的参数是 `y/p/org`，
FastAPI 据此把这三个当成**必填查询参数**，前端传的是 `year/period/org/months/basis`，
校验不过 → **422**。

**为什么本地没发现**：我验证时是**直接调函数** `cl.cost_ledger_dashboard(None, year=…)`，
绕过了 FastAPI 的路由与校验。函数本身没毛病，**坏的是它跟 URL 的绑定关系**——
这种问题只有走 HTTP 才暴露得出来。

**改法**：装饰器移回真正的处理函数（helper 提到装饰器之前）。

**顺带做了一次全模块审计**：把 `router.routes` 里每条路由绑定的 `endpoint.__name__` 全列出来，
逐条确认没有再绑到私有 helper 的。14 条全部正确。

**验证（这次走 HTTP，不再直接调函数）**：
`dashboard?basis=current` 200 / `basis=closed` 200 / 不传 basis → 默认 current 200；
`state` `cat-subjects` `orgs` 均 200。

**教训**：在装饰器与被装饰函数之间插代码是**静默劫持**——不报错、不告警，只在调用时以
参数校验失败的面目出现，离病因很远。新增 helper 一律放在**装饰器之前**或文件其它位置。
以及：**接口改动必须走 HTTP 验一次**，直接调函数验不出绑定问题。

# V2.367 · 临时工考勤 · 花名册缓存 / 通报文字上页面 / 期间以右上角为准

**日期**：2026-08-29　**分支**：main

## 一、花名册不再每次重建（「怎么还是取那么多人」）

使用者看到进度条停在「在职 1366 人」，问怎么还取这么多。**问得对，比例确实不合理**：
2026-07 只有 40 个人，建花名册要走 101 个部门 ≈ 380 次调用 / 90 秒，
而打卡本身才 1,240 次 / 40 秒——**建表比取数还慢**。

那一步在做什么得先讲清楚：汇总表上只有姓名，要换成钉钉 userid；
而钉钉**只能按 ID 反查姓名，没有按姓名搜人的接口**，所以必须先有一份全量对照表。

现在整份花名册（在职＋离职）落库缓存，判据是「**这批名字缓存里齐不齐**」：

```
第一次  缓存为空          → 重建，53 秒
第二次  同一批名字         → 「40 个名字全部对上，跳过重建」，0.1 秒
第三次  混进一个查无此人的  → 「有 1 个名字找不到（多半是新入职），重建花名册…」，54 秒
```

**不能无条件用缓存**——新入职的人不在里面，静默漏掉比慢更糟。所以只有当这批名字
一个不缺时才走缓存；缺人就重建一次并刷新缓存。稳态几乎零耗时，来了新人也不会漏。
进度文案也改成「正在建『姓名→钉钉ID』对照表（这一步不取打卡，只取姓名）」，
免得看着像在拉 1366 个人的考勤。

## 二、通报文字搬到第⑦步（经理直接来这儿复制）

⑦报告出具页顶部新增「用工成本汇总」块：按派遣方 × 车间的表格 ＋ 那段可直接发群的文字，
带**「复制全文」**按钮。

**与导出 Excel 用的是同一份后端计算**（`_cost_agg` / `_cost_text`，结果挂在 `res.用工成本`）。
两边各算一次迟早会对不上——2026-08 那条手敲的通报就是金额对、
两个车间的平均单价照搬了上个月，这种错最难看出来。

## 三、期间以右上角为准，识别到别的期间只提示

原来「选了文件会清掉右上角残留的期间」，于是右上角显示 8 月、实际按表标题跑成 7 月，
看着像工具没听指令（使用者反馈：「我左上角勾选的8月，他还是导了7月」）。

按定案改：**选文件不再清空期间，右上角就是准**。文件名里带的月份只用来**提醒**：

```
⚠ 右上角选的是 2026-08，但汇总表文件名像 2026-07。
   期间以右上角为准；真要核那一期，请先把右上角切过去。
```

这个提醒在点「开始核对」**之前**就出现，不用等提交后被后端拦下才知道。
后端原有的「识别月份与所选不一致就拦住」保留不动——那是防止按 8 月的合同价算 7 月的数、
还把 8 月的留档覆盖掉（V2.347 加的，真出过事）。

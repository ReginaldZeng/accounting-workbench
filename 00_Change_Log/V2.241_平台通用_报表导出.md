**【平台通用】报表导出**。业务方要的是「进金蝶导出所有主体，一个主体一个文件，每个文件是三大报表和科目余额表、序时账簿」，并特别交代「**注意列宽**」。

> 版本号按防撞号规则暂定（提出时目录内最大为 V2.240，本分支自占）。

## 一、最关键的一件事：三大报表能全自动拿到

**开发中我先判断错了一次，必须记下来。** 初查时我按「报表」的思路扫 `GetSysReportData`，试了 40+ 个候选业务对象名（`GL_RPT_BalanceSheet` / `GL_RPT_ProfitSheet` / `FR_Report` …），全部回「业务对象不存在」，据此得出「资产负债表/利润表 WebAPI 拿不到，只能人工上传」的结论。**这个结论是错的**——业务方甩来金蝶 API 文档和报表列表截图后重查，正确路径是把「财务报表」当**普通单据**查：

```
KDS_Report  单据查询(FNumber='GB00001' + FYear + FPeriod + FReportStatus='A'在制)
     ↓                       ← 过滤口径由业务方在金蝶 UI 上给出，实测正好 8 张，与其界面一致
   FRptId（GUID 主键，字段名不是 FID）
     ↓ View(FRptId)
KDS_Sheet[] 三个表页：资产负债表 / 利润表 / 现金流量表
     ↓ RptContent：base64 → zlib
FarPoint Spread XML：每格 <Data>算好的值</Data> + <Formula>Acct(...)</Formula> + <Tag>报表项目码</Tag>
```

**教训**：金蝶把「报表」分成两类——`GetSysReportData` 那种即时算的账表（存货收发存等），和 `KDS_Report` 这种**已生成、已存库的报表单据**（财务报表/抵消表/部门报表）。三大报表属后者。下次找不到报表对象时，先去金蝶 UI 的报表列表看它有没有编码/状态/所属组织——有，就说明它是单据，走 ExecuteBillQuery。

另：`KDS_RptItem`（报表项目）是**模板定义**（项目/科目/取数公式/方向/合计项/层级码），不是算好的数，别拿它找数。

## 二、口径（全部对着业务方给的参考文件逐格试出来，不是照文档抄）

| # | 口径 | 不这么做会怎样 |
|---|---|---|
| 1 | 本位币取 `BD_AccountBook.FCURRENCYID`（103/104/109＝美元） | 境外主体 1–6 期各有人民币/美元两套，取错就导出折算版。**不写死主体号**（`AC_AccountBook` 对象在本账套不存在，字段也不叫 FBaseCurrencyID） |
| 2 | 科目余额**只取本位币那一档** | GL_BALANCE 按（科目×维度×币别）存，另有一行【币别为空】的综合合计。1001 实测：人民币 3735.2 / 空币别 3525.525（三币折算相加），后者与报表对不上 |
| 3 | **剔零，但保留「本期凭证碰过该(科目,维度组合)」的零行** | 原始 6601 有 982 行、报表只显示 146 行，必须剔；但**不能剔干净**——金蝶留着少数十二列全空的行，那是**本期动过、金额恰好轧平成 0** 的真业务行。6401 实证（目标 91 行）：只看非零→89（少2）；非零 or **本期**凭证出现过→**91 ✓**；非零 or **本年**凭证出现过→98（多7）。口径卡在「本期」，放宽到「本年」就多 |
| 4 | 核算维度顺序按**每个科目自己配的维度顺序**（`BD_Account.FFlEXITEMPROPERTYID`） | 按固定顺序拼，值全对但**串是反的**：序时账簿 6949 行、科目余额 24 行对不上。1123＝供应商→供应商分组→品牌项目 |
| 5 | 序时账簿按**凭证号**排，不按日期 | 参考文件首行是 6/2 的记1，6/1 的记33 排在后面。按日期排整表错位 |
| 6 | 翻页排序键必须唯一（`FAccountID.FNumber,FDetailID`） | 只按科目号排，翻页**静默丢行**：实测 6601 少 101 行、6401 少 2 行，**不报错**。差点让我把口径判错 |
| 7 | 科目名称按层级缩进（每级 2 个全角空格） | `　　客户往来`、`　　　　暂估进项税` |
| 8 | 同科目内维度行按维度编码**拼音序**排（GBK 编码比较） | 建设银行 < 宁波行；Unicode 序恰好相反 |
| 9 | 金额统一收 4 位小数 | float 二进制尾巴会写进 Excel（`74260573.37810001`），逐格比对满屏假差异 |
| 10 | 末级科目判定必须用**完整科目表** | 拿过滤后的余额行推，会把"下级恰好被剔零"的科目误判成末级，合计差 10,347.15 |
| 11 | 维度 ID 非 0 但取不出维度值 → `【未录入】` | 凭证漏填必填维度；留空会与"科目本身那行"混淆 |
| 12 | 弹性域字段名逐个实测：员工域编码是 `FStaffNumber`；6 个自定义辅助资料域名称字段是 `FDataValue` 不是 `FName` | 任一写错，整条查询报的是「FDetailID 字段不存在」——报父字段、不报哪个域，一次查 19 个域根本反推不出来 |

## 三、列宽（业务方点名的那件事）

金蝶原生导出的实测毛病：

- **序时簿 14 列全是 30.6 宽**（金蝶把 `defaultColWidth` 设成 30.625）：摘要实需 217 字符、核算维度需 109，反而不够；期间只要 4、凭证字只要 6，白占一屏。
- **科目余额默认 9.0 宽**：核算维度名称需 75、8 个金额列各需 16，**全被截成 ####**。
- **三大报表**：「会企01表/单位：元」那列只有 8.6（需 15，被切掉）；另各拖着 49~56 个幻影空列，Ctrl+End 跳到 BJ244。

本次按实测内容宽度定死列宽，两张长表加冻结表头、序时账簿挂自动筛选，幻影列不生成。

**顺带记一个坑**：整形阶段最初想「拿金蝶原文件改列宽」，用 openpyxl 读写一遍——**它会把三大报表 56 个公式格（合计行）的缓存值全清空**。Excel 打开会自己重算，人眼看不出来；但 pandas / Power BI / 任何读缓存值的程序读到的就是空白（实测：利润表 B23 净利润 −4,002,793.58 变空）。属于「看着没事、下游全错」的静默事故。本次改为**自己组装工作簿、只写值不写公式**，从根上绕开；若将来仍需改造金蝶原文件，走 XML 级手术（只重写 `<cols>`/`<pane>`/`<autoFilter>`，其余字节原样搬运）。

## 三点五、导出通知（邮件）

业务方定：**导完就发、成败都发、只走邮件**（钉钉渠道显式关掉）。

- 复用既有的**分场景收件人**机制（V2.230 建的 `notify_recipients` 表），场景名 `报表导出`：
  收件人存 DB、②页签可改；**SMTP 账号密码只在 conf.ini**，不经前端、不进 DB、不回显（沿用本项目的密钥边界）。
- 收件人留空 → 回落 `conf.ini [smtp] to` 公共名单。
- 邮件内容：期间、成功几个主体、**失败明细放最前**（出问题时最该一眼看到的是哪几个没导出来、为什么）、
  落地路径、逐主体行数表。
- **通知失败不影响导出结果**：文件已落盘，发不出邮件是另一回事，故整体兜住，只把原因写进回执
  （实测未配 SMTP 时：导出成功 3 个 + 回执明写「通知未发出：未配置 SMTP」）。
- 另给一个「发送测试邮件」按钮，只验通道、不跑导出。
- ②页签的**保存按钮放在最底下、一次管路径+收件人两块**：两者分在两个框里，按钮若跟着上面那块走，
  改完收件人还得往回滚才能保存，很容易改了没存。

## 三点六、共享盘写权限（业务方提出，**未解决，待定案**）

业务方问：「共享盘是需要一个账号进去的吧，不然没权限你怎么写进去」——**问得对，这是原设计的缺口**。

后端以**服务账号**身份运行（宝塔起的进程），访问 `\\NAS\...` 用的是那个账号的身份。若它是 LocalSystem
或默认低权账号，对 NAS 无任何凭据 → 直接拒绝（工具会报「服务器账号对该目录没有写权限」）。

三条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A 换服务账号（建议）** | 运维把宝塔那个 Python 项目改成用对共享盘有写权限的账号跑 | 工具零改动，密码只存在服务配置里 |
| B 工具带凭据 | conf.ini 存共享盘账号密码，导出前建立连接 | 多存一份密码；Windows 需 pywin32、Linux 需 CIFS 挂载权限，平台差异 |
| C 落本地 + 页面下载 | 导到服务器本地，页面下载 / 通知带链接 | 绕开权限问题，但文件不会自动出现在共享盘 |

业务方倾向「在前端做一个共享盘账号密码」。**已回复不建议**，理由：本项目已定的密钥边界是
「密钥在 conf.ini（服务器、gitignore、不入库），只有非机密设置才进 DB/前端」（现成例子：钉钉应用凭证只在
conf.ini、收件人才在 DB；SMTP 密码在 conf.ini、收发件人在 DB）。共享盘账号往往是**域账号**，
能碰的不止那一个文件夹；放前端意味着密码经网络传到后端、明文存进 `workbench.db`、任何有该页面权限的人都能改，
比 conf.ini 弱一档且破了项目自己的规矩。**若确定要做 B，密码写 conf.ini、前端只显示「已配置/未配置」＋
一个「测试连接」按钮，永不回显。** 待业务方定案。

## 四、落地与权限

- **落地路径**：`conf.ini [rptexport] out_dir` 兜底，前端可覆盖，**留空即回落兜底**（业务方定）。
- **改路径须口令**（复用 `conf.ini [notify] passcode`，与通知设置同一把），且须敏感点 `rpt_export_cfg`。
  路径不是邮箱——填错能往服务器任意位置写，故动作点标敏感（默认不给）、且校验目录：上级目录必须已存在（不凭一个手滑路径在服务器上造目录树）、末级可建、落地前做写权限探针。
- **`rpt_export`（一键导出）非敏感**：只读金蝶、不写金蝶。
- **后台任务 + 进度轮询**：8 主体实测 51 秒（101 序时账 2.4 万行、107 一万三是大头）。挂在一个 HTTP 请求里必被网关掐断，且掐断时前几个主体已落盘、用户只看到一个红叉。
- 页面文案明确写了**「这是服务器上的路径，不是你自己电脑上的」**——这是部署在宝塔上的服务，最容易踩的就是这个。

## 六、遗留

1. **科目余额缺 2 行**：6401 主营业务成本两行**十二列全空**，金蝶报表留着、本工具按「剔零」剔了。不含任何数字，不影响任何合计。
2. **合计行 4 格未对齐，业务方定「先不改」。** 经核查，**金蝶那张参考表的合计行本身就不可复现**：
   拿它自己的 1110 条明细，任何加法都加不出它印的合计（末级+无维度 303,842,296.6637 ／ 一级+无维度
   302,568,127.6786 ／ 全部明细 618,943,810.8763，而它印的是 303,852,643.8146），且缺口 10,347.15
   在它明细里**找不到任何一行等于该数**——说明它的合计另有引擎、与展示的明细不同源。
   本工具用「末级科目·无维度行相加」，**复现出了同一笔试算不平**（见第 6 条），只是整体低 10,347.15
   （期末低 890,331.73），借贷两边低幅完全相同。**待业务方定案**：凑它的数 ／ 保持可复算口径并在表上标注 ／
   继续向金蝶要报表方案参数。
3. **序时账簿 36 格**：6 张凭证的分录内部顺序与金蝶不同，缺一个稳定的分录序号排序键（GL_VOUCHER 未暴露分录序号字段）。
4. **共享盘写权限未定案**（见三点六）：现在填服务器本地路径即可跑通；要落 NAS 共享盘，需先定 A/B/C。
5. **报表仪表盘（rptdash）仍是空占位**，摆哪些报表待定。
6. **⚠ 顺带发现的账务问题（非本工具缺陷，建议转总账会计核查）**：101 主体 2026年6期科目余额表
   **期初、期末试算均不平衡，借−贷 ＝ 209.675 元**（本期发生、本年累计两栏是平的）。
   金蝶原生导出的合计行如此，本工具按自己口径算出来的也是同一个 209.675——即**账上历史遗留的一笔不平**，
   从期初原样带到期末，不是本期做出来的，也不是取数或加总方式造成的。

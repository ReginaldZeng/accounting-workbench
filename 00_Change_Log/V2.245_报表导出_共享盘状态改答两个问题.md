## 现场

页面上那行写的是：

> 共享盘同步：立即同步 ↻ **2026-08-09 00:12:02** · 取件机 RPA · 本轮下载 0 个、已有 16 个

业务方看不懂，两个问题：

1. 选的是 **5 期、只有 8 个文件**，为什么写 **16**？
2. **本轮下载 0 个**，是不是没在工作？

## 为什么会看不懂：我报的是取件机的内部账，不是人要的答案

- 「本轮下载 N 个、已有 M 个」是取件机的**工作量流水**——它这一轮搬了几个、跳过几个。
  人真正问的从来不是这个。
- 那个 16 是**服务器上全部期间合计**。取件机每轮问服务器的是"你那儿现在总共有哪些文件"，
  **它不分期间**。而这行字又正好摆在"2026年5期"下面，被读成 5 期的数是必然的。
- 「本轮下载 0 个」其实是**正常稳态**（没有新东西要搬），却长得像出问题。

业务方直接给了正确的口径：**「1、共享盘最新的文件是什么时候的　2、是否有在工作」**。

## 改法：这一块只回答那两个问题

```
共享盘                                              立即同步 ↻
  最新的文件   2026-08-09 00:05:31  2026年05月/2026年05期_109_….xlsx · 共 16 个文件
  取件机       ✓ 在跑   23 秒前回报过 · RPA · 每分钟一轮
  ─────────────────────────────────────────────
  最近一轮：新搬 0 个、原样跳过 16 个（服务器上全部期间合计，不只本期；新搬 0 个＝没有新东西要搬，是正常的）
```

停了的时候：

```
  取件机       ⚠ 停了   已 47 分钟没回报（RPA）——那台电脑可能关机了，或定时任务被停了。
                        共享盘上的文件不会再更新。
```

### ① 「最新的文件」要取件机报

**服务器看不到共享盘**（整个取件机架构就是为这个而存在的），所以这项只能由取件机扫目标目录得来：
每轮结束时找出最新的一个 `*_财务报表.xlsx`，把**相对路径 + 修改时间 + 总个数**一起回报。
文件不多（一个月 8 个），每轮扫一次开销可忽略。

`.ps1` 与 `.py` 两版同步改；老版取件机不报这项，页面显示"取件机还没报过（升级后即有）"，
**不报错、不留空白**。

### ② 「在不在干活」要服务端算

新增 `_sync_view()`：把「距上次回报多少秒」`ago_sec` 和「算不算活着」`alive` 在**服务端**算好下发。
⚠ 这个差值**不能让前端拿本机时钟去减服务器时间戳**——两边差几秒就会出负数或跳变
（V2.241 的进度耗时踩过同一个坑，那次也是改成服务端算才稳）。

存活阈值 `_ALIVE_SEC = 240`：取件机每分钟一轮，留 3 轮容错，别一抖就报警。

### ③ 内部账降级

「新搬 N 个、原样跳过 M 个」保留，但降成底部小灰字，并补两句：
**「服务器上全部期间合计，不只本期」**（正面回答那个 16）、
**「新搬 0 个＝没有新东西要搬，是正常的」**（只在真为 0 时出现）。

## 一条通用教训

**别把系统的内部账当成给人看的答案。**「搬了几个、跳过几个」是取件机的自述，
而人站在这个页面前只有两个疑问：文件到没到、机器活没活。
这两个问题的答案，一个要跨网络去问取件机、一个要在服务端算时差——**都不是现成字段，
所以省事的做法就是把手头有的数字摆上去**。这次就是这么摆错的。

## 验证

浏览器实测三态，逐字核对文案：

| 场景 | 页面 |
|---|---|
| 在跑 | 最新的文件 2026-08-09 00:05:31 … · 共 16 个文件／取件机 ✓ 在跑 23 秒前回报过 |
| 停了 47 分钟 | 取件机 ⚠ 停了 已 47 分钟没回报…共享盘上的文件不会再更新 |
| 旧版取件机（无 newest 字段） | 最新的文件：取件机还没报过（旧版取件机不报这项，升级后即有）；其余照常 |

另：`新搬 0 个＝正常` 这句只在 copied 为 0 时出现（第三态 copied=1，实测已不出现）。
编码自查：`pull_reports.ps1` 仍是 UTF-8 **with BOM**、`pull_hidden.vbs` 仍是纯 ASCII（两者的既有约束）。

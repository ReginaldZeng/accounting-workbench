**【存货台账/看板】多期取数改逐期，修一处我自己引入的错数**。

**怎么暴露的**：业务方拿 3 月底稿与工具对，说"我给你的表格是对平的，你输出的不平"。
逐层查下来——底稿 11,914,577.88 ＝ **单期取数，分毫不差**；而看板显示 **11,915,738.06**。
**同一个月，看板和台账导出不是同一个数。**

**根因是 V2.254 我引入的区间取数**。当时为省调用次数走 `FIsDisplayPeriod="true"` 一次取整段，
**只验了区间末期 P5 与单期一致就上线了**。实测规律：

```
区间 P3–P3 / P3–P4 / P3–P5   3 月结存 11,914,577.88  ✓ 与单期一致
区间 P1–P3 / P1–P5 / P1–P12  3 月结存 11,915,738.06  ✗ 多 1,160.18（多 1 行）
区间 P2–P3                   3 月结存 11,914,591.48  ✗ 多 13.60
```

**只要区间起点早于该月，那个月就被带进前期残留，且起点越早带得越多。**
报表本身没问题——逐行比对（2,769 键）单期与多期完全一致；问题只在**跨期区间**这种取法。

**改法**：`fetch_inventory_period_totals` 改为**逐期各调一次** `fetch_inventory_summary`，
返回结构不变（调用方无需改动）。代价 5 期约 29 秒（原约 5 秒）。**这个代价必须付**——
看板与台账导出显示的必须是同一个数，否则整个工具的可信度就没了。
区间取数的坑与实测数据留在函数注释里当反例，别再"省一次调用"。

**验证**：P1–P5 逐期与单期取**五期全部一致**（12,485,138.29 / 13,155,666.72 / **11,914,577.88** /
12,645,632.27 / 10,958,051.26）；看板端到端 29.3 秒出数；内核单测 17/17 绿。

**教训**：只验一个样本点就上线。P5 恰好是区间末期、恰好对，于是"验过了"。
同类前科：V2.257 的勾稽②「生产退库」也是一个月验不出来（3 月没有这类单据、等式碰巧成立）。
**跨期/跨样本的东西，至少验两个不同位置的点。**

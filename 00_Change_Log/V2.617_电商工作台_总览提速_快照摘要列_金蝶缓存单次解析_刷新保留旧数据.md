# V2.617 电商工作台：总览提速——快照只读摘要不解压 ＋ 金蝶缓存一份只解析一次 ＋ 刷新时不清空页面

接 V2.583。现象：总览页长时间停在「正在汇总各店铺数据…」，四张卡和店铺表全是"—"。

查因（两个叠在一起）：
1. **后端每次开总览都在做重活**。逐店读「数据准备」卡片时，把每类资料的整份快照（订单报表两万多行、宝贝明细两万行、出库七千行）从库里搬出来、解压、解析 JSON，只为数一下行数和状态；金蝶应收缓存（上万行 JSON）7 家店各读一遍，虽然除天猫外一家都匹配不上。本地按真实列宽（60 列）模拟单店数据：一次总览 **1.27 秒**；服务器是 MySQL、机器更慢，只会更长。
2. **前端每 5 秒轮询一次都把页面清空重画**。任一店铺核算结果处于「生成中」时总览每 5 秒重取一次，而取数钩子在重取期间把上一份数据置空——于是接口慢一点，用户看到的就是大部分时间一片"—"。

## 改法
- **快照表加 `summary` 列**（`ec_workbench_imports.summary`：行数 / 是否可用 / 告警）。上传落库时顺手算好写入；数据准备与总览只读这一列，不再取 payload。V2.617 之前存的老记录没有摘要：第一次读到时解压一次算出来回写（同一连接内提交，避免 SQLite 读写互锁），以后就不用再解压。建表迁移照 `_ensure_ec_shop_map_cols` 同款（SQLite / MySQL 都补列）。
- **金蝶应收缓存改共享读**：`ec._kd_cache_rows(period)` 按文件 mtime/size 缓存已解析的行，同一份缓存文件进程内只解析一次；「只读同步」落盘走 `os.replace`，换文件即自动换新。收入确认核算、数据准备的金蝶行、收款核销跑批三处统一改用；调用方只做筛选不改行。
- **前端总览取数加保留键**：轮询、点「刷新数据」时保留上一份数据，面板右上角改显"正在更新…"，不再把卡片和表格清成"—"；「资金账户余额」同样处理。首次打开仍显示"正在汇总各店铺数据…"。

## 口径不变
只改"怎么取"，不改"取什么"：卡片可用性判据（rows 非空且 status 为 ready/warning）、行数、告警文案与改前逐项一致；金蝶行内容不变；总览合计逻辑不动。

## 验证
- 本地基准（7 家店、天猫店四类快照 + 1.5 万行金蝶缓存，SQLite）：总览一次 **1.27 秒 → 0.02 秒**（首刷含解析金蝶缓存 0.06 秒）；窄列数据 0.21 秒 → 0.02 秒。改前改后卡片输出逐项相同。
- 老记录回填：把 summary 清空后再读，卡片与改前一致，第二次读不再解压；快照损坏的记录仍给「已保存快照不可读」黄卡不崩。
- 后端单测：tests 下电商相关 27 个 + kernels 下 23 个全过。前端 `vite build` 通过（bundle 已随提交）。
- 未在真机跑浏览器回归（本机无 playwright 模块）；前端改动仅取数钩子保留键与一处文案。

## 发布
改了后端 .py 与前端 bundle：自动部署会重启后端；建表迁移在启动时自动补列；用户 Ctrl+F5 拿新前端。回退＝反向提交本提交（summary 列留着无害）。

# V2.412 · app_settings.v 加宽 LONGTEXT——修「全量月留档在 MySQL 上静默失败」

**日期**：2026-08-30　**分支**：main

Reginald 实测：六月全核完了，但 6 期一直「未核」、历史复核结果只有 7 月。

## 病根：开发/生产库差异（SQLite 无上限 vs MySQL 的 Text=64KB）

临时工「按期留档」把结论快照压缩后写进 `app_settings.v`（`db.set_setting`）。该列类型是 `Text`：
- **SQLite（本机开发）**：TEXT 无长度上限 → 一直好，从没暴露。
- **MySQL（服务器）**：`Text` = **64KB 硬上限**。

六月是**全量月**（300+ 人、16,816 工时），结论 JSON 压缩后仍 >64KB → MySQL 拒收/截断 →
`_save_period` 的 try/except 吞掉异常（留档失败不影响核对结果）→ **大月静默丢档**。
七月只有植物肉 40 人，压缩后塞得进 64KB → 正常留档。这就是「七月已核、六月核不进」。

## 改法

- `db.py`：`app_settings.v` 改为 `Text().with_variant(LONGTEXT(), "mysql")`——MySQL 用 LONGTEXT（4GB），
  SQLite 仍是无上限 TEXT，互不影响。新装的库直接就是宽的。
- 既有 MySQL 库：`create_all` 不改既有列，故加 `_ensure_app_settings_wide()`（同 `_ensure_user_columns` 套路）：
  启动时若发现 `v` 还不是 LONGTEXT 就 `ALTER TABLE app_settings MODIFY v LONGTEXT`（幂等、仅 MySQL 动手）。

## 校验

- 本机 `import db` 正常；MySQL 方言编译 `app_settings` 建表 DDL = `v LONGTEXT`；SQLite 侧不变。
- 服务器可先手动 `ALTER TABLE app_settings MODIFY v LONGTEXT;` 立即解封（不必等部署），再重新点「开始核对」，
  六月即留档；本版部署后该 ALTER 也会在启动时自动执行，任何机器都不再撞 64KB。

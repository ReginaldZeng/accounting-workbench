**【平台通用】补登记 BP 四个权限码，`/api/bp-perm-drift` 归零**

## 起因

BP 工作台侧对账（2026-08-16）发来交接单：BP 在 `auth.py::PERMISSIONS` 注册码、核算在
`db.py::CAP_META_STATIC` 登记同一批码，**两边手抄**，漂了 4 个：

| 码 | BP 何时加的 | 漏登记的后果 |
|---|---|---|
| `bp:board:askData` | V2.183 | 「AI 问数」板块授不出去 |
| `llm:call` | V2.178 | 大模型相关功能授不出去 |
| `perf:trace` | 早于 V2.106 | 驾驶舱明细溯源授不出去 |
| `weekly:send` | V2.146 | 业绩周报发送授不出去 |

漂移**不报错**，只表现为「某功能对某些人静默不可用」——账号管理页勾不到该码，
于是除主管理员（透传 `*`）外没有一个人能被授予。这正是 V2.106 建
`/api/bp-perm-drift` 对账接口时记下的教训，本次是同一个坑的第二次复发。

## 改法

`CAP_META_STATIC` 补 4 条：1 个板块准入码（tier=nav）+ 3 个功能点（tier=act）。

- `bp:board:askData` 自成一组「智能分析中心」——BP 侧它是**一级导航组**（与经营管理报表同级），
  不是挂在报表下的二级。
- 3 个 act 码的 `mod` 分别指向 `bp:board:askData` / `bp:board:budgetCockpit`，
  已校验都指向真实存在的板块码（避免 V2.240 那种「mod 指向已撤菜单 → 掉进账号页第③栏
  『不受菜单门控』堆里恒显示」的幽灵权限）。

### sensitive 怎么定（**没有照抄 BP，这是本次唯一的判断题**）

交接单把「CAP_META 的 `sensitive`」与「BP 的 `SENSITIVE_PERMS`」当成了一回事，
说标敏感会让带 `*` 的管理员也调不了。**核对代码后确认这两者是两件事**：

| | 管什么 | 谁是真相源 | 漂了谁报 |
|---|---|---|---|
| `BP_SENSITIVE_CODES`（db.py） | BP 的 `has_perm` 里「`*` 不覆盖、须逐个显式透传」 | BP 的 `SENSITIVE_PERMS` | `bp_registry_drift().superSensitiveGap` |
| `CAP_META` 的 `sensitive` | **核算侧**默认给不给（`default_perms` / `_backfill_missing_perms` 跳过、账号页高亮） | 核算自己的业务口径 | 不参与对账 |

所以在 `CAP_META` 标 `sensitive` **不会**让主管理员的 `*` 失效、不会造成
「显示有权、点了 403」。它只影响「新账号/存量账号默认发不发」。

据此定：

- **`llm:call` 标敏感（与 BP 注册表不同，核算侧主动收紧，业务方 2026-08-16 定）**。
  理由：`_backfill_missing_perms` 会把非敏感的 `ws=bp` 码按 `default_perms` 自动补给
  **全部 BP 组存量账号**，而大模型是**按 token 真金白银花钱**的——照抄「非敏感」等于
  全组当场获得烧 token 的权限。BP 自己的注释也写着「门户接头做好后，只给需要 AI 功能的
  角色发这个码即可收紧」，接头已经做好，就是现在。
  且这个方向更好收：先发再想收要逐人取消勾选，默认不给则随时能加。
  （同 `cost_ledger_fetch` / `ec_settle_upload` 先例。）
- **`perf:trace` 不标敏感**——照 BP 原话「常规 feature 点，`*` 覆盖」。它只是把看板上
  已经看得见的汇总数下钻到来源行，不写不发，同核算侧「导出不单设点」的惯例。
- **`weekly:send` 标敏感**——对外发邮件/群消息，同核算侧一切外发/写外部系统的动作
  （`logistics_post` / `fxrate_post` / `ec_post`）。
  ⚠ 注意 BP 侧 V2.150 已把它**移出** `SENSITIVE_PERMS`（原因：门户只注入 `*`、敏感点
  `*` 不覆盖 → 按钮永远灰），故它**不进 `BP_SENSITIVE_CODES`**。BP 那边另有口令
  `BP_WEEKLY_SEND_CODE` 作真闸，这个码只管按钮显隐 → 双闸。

`BP_SENSITIVE_CODES` 本次**一个字没改**——BP 的 `SENSITIVE_PERMS` 仍是原来 6 个。

## 验证

离线复刻 `bp_registry_drift()` 的比对逻辑（直接 AST 读两侧源码，不 import `db.py`——
import 会建 sqlite 文件）：

```
BP 码表：22 个（板块 12）  核算已登记：22 个
missing           = []
extra             = []
superSensitiveGap = []
ok                = True
```

四个新码在 BP 组存量账号上的默认行为（`_backfill_missing_perms` 按此补齐）：

| 码 | sensitive | 存量 BP 组自动获得 |
|---|---|---|
| `bp:board:askData` | 否 | **是**（同其余 11 个 `bp:board:*`，一贯行为） |
| `llm:call` | **是** | 否（须逐人授予） |
| `perf:trace` | 否 | **是** |
| `weekly:send` | **是** | 否（须逐人授予 + BP 侧口令） |

`mod` 指向校验：3 个 act 码全部指向存在的板块码。

**待线上验证**（本机 BP 未起，`/api/bp-perm-drift` 走的是静默降级分支）：
部署后跑一次 `GET /api/bp-perm-drift`，期望 `ok=true`；
并到账号管理页确认 4 个码可勾选、`askData` 落在「智能分析中心」组下。

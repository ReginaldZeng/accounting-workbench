## ① 货损明细的「备注」＝ 出库单表头的 FNote

底稿那列手工填的是钉钉审批单号。金蝶里它在**单据表头的备注字段**，不在流水表里——
流水表是按物料展开的行，表头字段不下发。所以要拿单据号回查一次单据：

```
ExecuteBillQuery  STK_MisDelivery / STK_MISCELLANEOUS   FBillNo,FNote   每批 100 个单号
```

🧪 7 月 QTCK011302 → `202606041716000281241`，与业务方底稿一致。

列序仍是 V2.309 定的那套（业务方：「归属挪到备注后面，前面几列完全不变」）：

```
原单编号｜类别｜产品项目｜物料编码｜物料名称｜规格型号｜基本单位｜发出数量｜单位基本单价｜金额｜仓库｜备注
　　　　↑ 前 12 列与业务方底稿逐列一致 ↑          ｜归属｜批号｜存货类别｜事务类型｜日期｜凭证字号
```

**顺手修一条会变"假绿"的测试**：`test_material_rows_written_once_per_bill` 原来写死数 A 列的
"管理费用·货损"。V2.309 把归属挪到 M 列之后，它数到的是 0 行——而断言恰好是 `assertEqual(n, 5)`
才没放过去。改成按表头名定位列：写死列号的断言一旦列序变动就悄悄失效，比断言失败糟得多。

## ② 新增「原始·完工入库流水」——勾稽②终于有底表了

成本勾稽三道，业务侧的底表此前只有①③有（就是「原始·制造费用明细(接口)」那张成本计算单），
**②的 6,179,892.86 是个孤零零的数、点不进去**。

整张收发存流水十几万行、不落库也不导出（这条口径不变），但②只用得到三种事务类型：

| | |
|---|---|
| 全表 | 11,984 行 |
| 汇报入库 | 223 行 |
| 生产入库 | 2 行 |
| 生产退库 | 0 行 |
| **落库/导出** | **225 行＝全表的 1.9%** |

1.9% 的代价换②可追溯，划算。且**用的是同一次取数**——`fetch_business_type_summary` 本来就要
把全表拉下来做汇总，顺路把这三种的明细行收下即可，不多打一次接口。

🧪 7 月三道勾稽全过、差异全 0，②的业务侧与新页合计**完全相等**：

```
① 制造费用归集  5101 借方 1,963,089.42 ↔ 成本计算单            1,963,089.42  差 0
② 完工结转      5001 贷方 6,179,892.86 ↔ 原始·完工入库流水     6,179,892.86  差 0
③ 投入归集      5001 借方 6,186,208.71 ↔ 本期投入＋在产品调整  6,186,208.71  差 0
```

**②那行的事务类型清单改成由 `WIP_CREDIT_BTYPES` 生成，不再手写**：这个常量是"发现一个补一个"的，
V2.307 加了「生产入库」而那行说明文字还停在"汇报入库＋生产退库"——**说明与实算已经对不上**，
只是没人注意。手写的口径说明迟早会撒谎。

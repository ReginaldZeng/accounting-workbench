**【平台通用】后端 app.py 按工具线拆分——从 5006 行单文件拆成 core.py + routers/ 五模块**。
**起因**：`app.py` 一个文件装下全部 7 条工具线的 100 个路由，最近 60 次提交里被改 18 次，是并行开发的
头号合并冲突源：两条不相干的需求（比如物流计提改税率、汇率录入改通知）也会因为都动这一个文件而撞车。
**先做了依赖体检**（AST + symtable 静态分析，非肉眼）：282 个顶层名里**真正跨工具线共用的只有 12 个**，
各工具线的代码在文件里本就是连续区块——耦合远比行数吓人的样子轻。另确认**全库零 `global` 语句**、
`CFG` 一律 `CFG.update()` 原地改，故 `from core import CFG` 不会拿到过期绑定（这是此类重构最经典的翻车点，
事先排除了）。
**改法**：①新建 `core.py`（249 行）收共享内核——路径常量 · 全局配置 CFG · 会计期间 · 缓存 ·
期间封存拦截 · 金蝶取数定格 · 登录/权限判定 · 金蝶状态码中文表；②新建 `routers/`，一条工具线一个模块：
`logistics_accrual.py`(273) · `archive.py`(272) · `fxrate.py`(717，含自动跑批调度线程) ·
`logistics_recon.py`(160) · `cost_ledger.py`(990)；③`app.py` 2508 行，只留平台域（登录/账号/权限/导航/
期间/银行对账/理财对账/科目余额/资金看板）+ `include_router` 清单 + SPA 兜底；④依赖方向单向
`app.py → routers/* → core.py`，core 不 import 任何 router，永不成环。
**验证**（改动只搬位置、不改逻辑，故全部验证围绕「行为零变化」）：
①**OpenAPI 全量比对 115 条路径+方法，改前改后完全一致**，一条不多不少；
②搬运脚本内置断言——router 若引用了留在 app.py 的名字直接报错，确保不会出现循环依赖（执行中真的挡下过一次边界错误）；
③`kernels/` 单测 **82 项全过**；④起真 uvicorn 冒烟：`/api/health` 200，五条工具线路由各返 **401**
（＝路由在、被登录门拦下，不是 404），`/some/spa/path` 200 ＝ SPA 兜底仍在最末、注册顺序没被打乱。
**收益**：今后改某条工具线只动 `routers/<线>.py`，`app.py` 只在新增工具线时加一行 include_router。
**遗留**：①平台域（导航/权限/期间/银行对账）仍在 app.py，这部分改动仍会互撞——但它天然是「一次只该有一个人动」
的东西，不建议并行，故本次不拆；②`app.py` 顶部的 import 头是历史全集，拆分后部分 kernels 导入已不再使用，
留着无害、未清理，以免与在途分支产生无谓冲突。

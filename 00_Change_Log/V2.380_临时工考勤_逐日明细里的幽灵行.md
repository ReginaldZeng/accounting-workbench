# V2.380 · 临时工考勤 · 清掉逐日明细里 1,200 多条幽灵行

**日期**：2026-08-29　**分支**：main

Reginald 筛出艾想清一个人，看到：

```
7日  19:48 → 次日08:33   3次  上报 11  ✓ 打卡撑得住上报
8日  08:33 → —          1次  上报 0   △ 仅1次打卡且未记工时，疑似无效
```

然后说：「你能不能好好检查」。**8 日那条是 7 日夜班的下班卡**，7 日那行已经把它算进去了，
不该再单独摆一行。这次不再一条一条等他发现——把逐日明细整表体检了一遍，找出三类幽灵行。

## 三类幽灵行（2026-06，共 1,208 条）

**① 夜班的下班卡被当成第二天一行 —— 142 条**
`compute_shifts` 早就算出了「次日整天都属于这一班」（`used`），但**没往外传**，
逐日循环照样为那天摆一行。现在把它带出来（`_Shifts.consumed`），
这天没上报工时就不摆。

**② 按业务线拆行的人，双方都没排班的日子被摆了两遍 —— 61 组**
V2.379 只处理了「一行有工时、另一行 0」；两行**都**是 0 的日子仍然各摆一条。
现在同一个人同一天的「没上报工时」行只摆一条。

**③ 跨月的夜班尾巴 —— 126 条**
1 日凌晨那几张卡属于上个月 31 日的夜班，本月数据里根本没有那一晚，`consumed` 盖不住。
判据：这天切不出班次、没上报工时、且**所有打卡都落在夜班下班窗口内**（凌晨到 11:30）。

## 一条差点放跑的真发现

③ 的第一版没限定班型，把**白班**的人早上那张孤零零的上班卡也吃掉了——
苏兵 7/7 只有一张 07:35，那正是该报的「仅1次卡·疑似无效」。
==单元测试当场抓住（3 条真表回归挂掉）==，加上「只对夜班/白夜混合生效」才对。
写规则时按现象归纳，很容易连正常情形一起吞掉；真表回归就是拦这个的。

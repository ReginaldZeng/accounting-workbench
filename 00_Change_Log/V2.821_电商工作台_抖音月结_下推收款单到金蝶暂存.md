# V2.821 电商工作台·抖音月结：下推收款单到金蝶「暂存」——电商这条线第一处写金蝶

接 V2.816。用户 2026-10-05 定了分工「金额完全一致的系统批量处理，两边说法不一样的交给会计」，并在三个选项里选了「工作台直接往金蝶下推收款单」。
此前这条线全程金蝶只读（「不自动做账 / 下推 / 核销 / 结账」）；本版是用户本人改的规矩，范围只到下面写明的这一步。

## 做到哪一步为止
**只把收款单备到金蝶「暂存」。不保存、不提交、不审核。**
- 暂存单没有单号（不占收款单编号）、不占应收的关联额度，删掉不留痕。
- 会计在金蝶里打开看过，自己保存 → 提交 → 审核；审核那一刻金蝶才核销应收、才出凭证。
- 「系统替人保存审核、等自动凭证、补转费用分录」是下一步，本版没有做，也没有试。

## 动手前在正式账套实测过的（2026-10-05，经用户同意，均已删干净）
- 3 张应收试推：下推规则 `AR_recableToRecBill`（与会计手工下推同一条），接口账号「系统操作员」有权限，2.7 秒；生成的收款单状态暂存、无单号，源单明细的关联与手工下推一致；默认收款明细是一张应收一行、结算方式和账户为空。
- 用「暂存」接口把收款明细改成「支付宝到账一行 + 内部转销每种扣款一行」、业务日期改月末：成功，源单明细不受影响。
- 100 张再推一次（1.7 秒 + 改明细 0.5 秒），留给用户在金蝶里看过后删除。
- 全程三张 / 一百张应收的核销状态、关联收款金额都没变。

## 这版做了什么
抖音月结页多一块「下推收款单到金蝶（暂存）」：
- **只推最干净的应收**：可核销、蓝字、已审核、从没核销过、订单（含合单组）里没有红字、钱是本期结算的、两边按分对齐。本次收款＝应收全额。
  9 月：可下推 16,070 张 ¥759,065.50；可核销但不推的 43 张 ¥800.47（订单里有红字，要先红蓝对冲，留给会计）。
- **分批**：每批默认 500 张，管理员可在 1–10,000 之间改（10,000＝金蝶一张收款单最多挂的源单行数，这样一次下推正好一张收款单）；每批自带到账行和扣款行，「收款明细合计 = 源单应收合计」。
- **金蝶会自己拆单**：一张收款单最多挂 10,000 行源单，超过就拆成几张（实测 16,070 张 → 10,000 + 6,070）。每批上限因此定为 10,000；万一金蝶仍然拆了，系统读回每张里实际挂了哪些应收，各算各的收款明细，每张各自两边平；备注里写「第 1/2 张」。
- **两个按钮**：「只推这一批」和「全部推完」。全部推完＝按每批张数一批接一批自动推到没有为止，每批一张收款单；中途哪一批出错就停在那里，前面推成的保留。9 月每批设 10,000 时自动跑两批（10,000 + 6,070）。
- **后台跑**：点下推后在后台进行，页面显示进度（复核 → 金蝶下推 → 改收款明细），可以离开页面；不受网页等待时间限制（下推那一步最多等 30 分钟）。
- **中途断了不留不明不白的东西**：下推请求如果中断，系统去金蝶找这段时间新冒出来的暂存单并删掉；删不掉或之后才冒出来的，页面上会列成「没登记的暂存单」，可以一键删。
- **先看后做**：页面始终显示下一批会建成什么样（几张应收、单号范围、每一行的结算方式 / 账户 / 金额 / 摘要、两边平不平）。
- **三档开关**：关 / 演练 / 真做，默认演练。演练档点下推会被拦住、不碰金蝶。只有管理员能改档位，改动留痕。
- **真做时**：推之前到金蝶逐张复核这批应收（未核销、已审核、没作废、没被别的收款单关联、金额没变），有一张变了整批不推；下推必须恰好生成一张收款单，否则全部删掉；改收款明细失败会把刚建的暂存单删掉。
- **留痕与撤回**：每批记下谁、何时、哪些应收、金蝶内码、用时；页面显示每批在金蝶里的现状（暂存 / 已保存 SKD… / 已审核·已核销 / 已被删掉）。还在暂存、没单号、接口账号建的可以一键撤回（删掉金蝶里那张暂存单）；会计保存过的系统不动。
- **不重复推**：金蝶里还在的批次里的应收不再进下一批；被删掉的批次，其中的应收自动放回。
- 收款单填法照会计 8 月抖音那张：结算方式 支付宝 `JSFS32_SYS` + 账户（照该店最近一张收款单认）/ 内部转销 `JSFS41_SYS`；收款用途 销售收款；扣款行的费用项目 `F_ora_Base` 填「电商」`FYXM001.001产品销售002`；业务日期填期末；备注写明是工作台下推、几张应收。

## 页面按「谁来做」重排（同版）
用户看到页面上那张整月的「收款单草稿」后说「总感觉这整个项目有点奇怪……这个收款单草稿，用途是什么」。
它是工具还只读时做的——给会计照着手工做一张整月收款单；改成系统分批下推后，它和实际建出来的单子不是一回事（整月一张 vs 五百张一批、到账行口径不同、含不含千川），留着只会误导。页面一天里叠了四层（只读对账 → 给依据 → 认合单 → 系统下推），同时在干「给结论 / 给人照着做的草稿 / 系统自己做」三件事。

重排成三块：
- **① 系统替你做的**：下推面板（能推多少、下一批、已推批次）。
- **② 要你处理的**：一张事项表——金额对不上、金额对得上但系统不推（订单带红字等，新增筛选项）、该结没结、没有平台订单号、钱结进来但金蝶没应收、不挂在订单上的账户进出；每项有数量、金额、说明，点「看清单」直接筛出下面的应收单明细。
- **③ 用来核对的**：账户余额核对；「账户进出汇总」（货款结算到账 − 不挂订单的进出 ＝ 本月账户净变动，另列结算时平台直接扣掉的费用）；本月结算订单两边各多少。

「收款单草稿」这个名字和面板去掉；导出 Excel 第一页相应改成「本月账户进出汇总」，新增一页「可核销但系统不推」。分类卡片保留在最上面。计算口径没有变化，只是摆放和命名。

## 口径
- 到账行 ＝ 这批订单本期结算进账户的钱；扣款行 ＝ 这批订单结算时扣的平台服务费 / 佣金 / 招商服务费 / 站外推广费。
- **不挂在订单上的账户进出不进任何一批**（9 月共 ¥78,400.85：千川充值 50,000、货款直投千川 23,158、运费险 2,772.78、评价有礼 1,754 等）。用户说千川先不管；页面上明确提示这一块要另外入账，在这之前金蝶账面余额会比流水余额多出这一块。
- 钱是更早月份结算、应收却一直没核的，不推——那个月的到账已经随当月收款单入过账，再算一次会重复。

## 验证
- 单测 10 个全过（新增：只挑干净蓝字、按批取数、批内两边相等、推过的不再取、红字 / 部分核销 / 未审核 / 更早月份结算的不推）。
- 本地（演练档，不碰金蝶）：下一批 500 张 ¥14,348.20，到账 13,937.92 + 四项扣费 = 14,348.20；演练档点下推返回 400；改每批张数生效；页面显示正常。
- **「真做」经页面接口在正式账套分步实测（2026-10-05 晚，用户同意，每步都撤回、金蝶里已清干净）**：

  | 张数 | 金额 | 金蝶下推 | 全程 | 生成收款单 | 撤回 |
  |---|---|---|---|---|---|
  | 3 | 164.70 | 3.5 秒 | 4.4 秒 | 1 张 | 1.3 秒 |
  | 2,000 | 76,928.58 | 8.7 秒 | 10.2 秒 | 1 张 | 3.2 秒 |
  | 5,000 | 219,578.23 | 23.0 秒 | 26.9 秒 | 1 张 | 3.6 秒 |
  | 16,070（全部） | 759,065.50 | 82.1 秒 | 96.1 秒 | 2 张（10,000 + 6,070） | 9.9 + 3.9 秒 |

  每一步：收款单状态暂存、无单号、业务日期 9/30；源单行数与金额、收款明细合计都与记录一致；扣款行的费用项目 `F_ora_Base`「电商」写进去了；撤回后金蝶里查不到、抽查应收仍未核销、关联收款为 0。
  第一次全推时系统还只认「恰好一张」，金蝶拆成 2 张后按设计把两张都删了并报错；随后改成支持拆单，重推通过。
- 「全部推完」的连推用每批 3 张、连推 2 批验证：两批应收不重叠、各自两边平，撤回后干净。每批设 10,001 被拒绝。
- 用户知情并接受的痕迹：金蝶上机操作日志里，下推时每张应收一条「生成收款单」、撤回时有删除记录，操作人系统操作员；今天全部试验合计约 4 万条。
- 未验：MySQL 生产环境；会计在金蝶里打开 / 保存 / 审核一张挂 10,000 行源单的收款单卡不卡、保存时校验过不过；下推请求中断后的自动清理（代码有，没真遇到）；多人同时点下推（有锁，未做并发实测）。

## 上线后建议的第一次用法
管理员把每批改成 3 张、档位改成真做 → 推一批 → 到金蝶收款单列表按「暂存」找到它核对 → 回页面点撤回 → 确认金蝶里删掉了。没问题再按需要把每批调大，最多 10,000 张；9 月的 16,070 张要推两次（10,000 + 6,070），得到两张收款单。

## 已知局限
- 带红字的订单（先红蓝对冲、蓝字只收净额）不支持，留给会计。
- 只有抖音店。天猫的收款单有两个收款账户、扣款种类多得多，未做。
- 下推记录存在服务器文件里，不在数据库。

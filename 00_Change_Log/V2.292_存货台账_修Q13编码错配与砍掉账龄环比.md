## Q13 修掉：物料编码与存货类别改成报表直出

### 病灶

跨维度报表的请求里**根本没要物料编码和存货类别**——取回名称与规格，再拿 `(名称, 规格)`
去物料档案 `BD_MATERIAL` 反查编码与类别。同名同规格的物料一撞，整行就挂到别人名下。

🧪 107/2026-3 与业务方底稿逐物料比（修前）：**109 个物料的结存金额两两对调**，例如

```
300100403  你 63,711.85   我 0.00
T00000047  你 0.00        我 63,711.85
```

**合计不受影响**（期初/收入/发出/结存四项与底稿分毫不差、三道勾稽一直全过），
所以错了一百多个版本没被发现——而"逐行能追"恰恰是台账的用处。

### 为什么当初没直接取

`kingdee_client.fetch_material_categories` 的 docstring 里写着一句**错的结论**：

> 「收发存跨维度报表本身给不出物料编码——实测 `FMaterialId` 被接受但恒返回空串，
> `FMaterialNumber`/`FNumber`/`FMaterialCode` 等则直接被报表服务拒绝。」

四个候选名都不对，就此收工——**唯独没试 `FMaterialBaseId`**。而「按日期」报表一直在用
`FMATERIALBASEID`/`FMATERTYPE`，只是跨维度这张表的命名风格是驼峰，没人想到去试同一对名字。

2026-08-13 实测（只读探针，10 个候选名逐个试）：

```
FMaterialBaseId  ✓ ['1002000008', '103010004', …]     ← 就是它
FMaterType       ✓ ['低值易耗品', '原材料', …]
FMaterialId      ○ 接受但恒空          FMaterialNumber ✗ 字段不存在
FMaterialCode    ✗                     FMaterialType   ✗
FMaterialCategory ✗                    FInvCategory    ✗
```

**教训**：几个候选名都被拒，只说明"这几个不对"，不等于"这张表没有这个字段"。
把"我没找到"写成"它没有"，下一个人就不会再找了。docstring 已按此改写。

### 改法

不是"换个更好的匹配键"，是**根本不需要匹配**：报表和编码同源，没有撞名的余地。
`fields` 补 `FMaterialBaseId,FMaterType`，列序整体右移，**物料档案那次 join 整个删掉**。

### 实测（107/2026-3）

| | 修前 | 修后 |
|---|---|---|
| 逐物料比结存金额（1,568 个物料） | 对不上 **109 个** | 对不上 **0 个** |
| 类别为空（nomap） | 靠档案兜底 | **0 行** |
| 三道勾稽 | 库存商品 0／原材料 1.92／周转材料 -1.92 | **完全相同** |

勾稽结果一格没变 → **只把行挂对了人，没动任何合计口径**。

剩下的类别差额（产成品 -22,981.27／包材 -102,495.38／原材料 +102,497.30…）**净额正好 0**，
是 **18 个物料被重分类**（空白纸箱 原材料→包材、纤蔬脆 委外半成品→产成品…）——
金蝶报表按**当前**档案追溯归集历史月份，已有「类别漂移」在报（D20/§9），不是错数。

`fetch_material_categories` 保留（别的取数线可能要读物料档案），但标注存货台账已不再用它。

**【存货台账】修一次由我造成、并被自己的容错设计藏了四个版本的残缺**。

**事故**：V2.280 改多期取数时，我用**字符串切片**替换 `fetch_inventory_period_totals` 的函数体——
起点是它的 docstring 末尾、终点是 `def fetch_account_books(`。而这两个锚点之间**夹着后来新增的 5 个函数**：
`fetch_inventory_bydate`（勾稽①）、`fetch_cost_calc` / `fetch_cost_gl`（第⑧步制造费用）、
`fetch_pnl_details`（第⑦步损益归集）、`_num_or_zero`，连同 `RPT_COST_CALC` / `_PNL_BILL_RE` 等常量，
**一并被切掉**（该次提交 -285 行）。

**为什么四个版本没人发现**：取数处一律 `except Exception as e` → 软失败给一行黄字。
于是 `module 'kingdee_client' has no attribute 'fetch_pnl_details'` 被显示成
**"损益归集取数失败（第⑦步将显示缺失）"**——看着像金蝶那边的问题，实则本地代码没了。
内核单测只测算法、不碰 `kingdee_client`，也照样全绿。
**V2.280 / 281 / 282 / 283 / 284 五个包都带着这个残缺发出去过**，业务方已部署 V2.284。
直到业务方问"这个明细还是导不出来吗"，我去查才暴露。

**影响面**：🅰 一键取数通道少三样——勾稽①两表互勾、第⑦步损益归集、第⑧步制造费用（连带成本三道勾稽）。
三者都只表现为一行黄字提示，**不影响已出的数的正确性**（缺的是没算，不是算错）。
🅱 上传通道与存货三道勾稽中的②③不受影响。

**改法**：
1. 从 `3467d0f~1` 取回那 230 行整段放回原位，逐个断言 11 个函数与 4 个 formid 常量都在。
2. **代码错误不再降级**：新增 `_CODE_BUGS = (AttributeError, TypeError, NameError, ImportError)`，
   四处取数点先 `except _CODE_BUGS: raise` 再 `except Exception` 软失败。
   **金蝶/网络/数据问题给提示；代码坏了直接炸**——这类问题必须在测试和页面上炸出来，不能装成外部故障。
3. 新增 `kernels/test_api_surface.py`（4 例）：断言路由依赖的 11 个函数存在、关键参数名在、
   4 个 formid 常量没被改错、多期取数确实是逐期调用。**删函数会立刻红，不必等真去调金蝶。**

**顺带完成业务方要的**：《原始·货损与处置明细》由**凭证级改物料级**——单据号回查收发存流水表补齐
物料编码/名称/规格/存货类别/物料分组/单位/仓库/批号/数量/单价。**不额外打接口**（流水表本来就在取，
把单据号一起递进去顺路带回）。🧪 2026-3 六行与业务方底稿**逐行一致**，合计 18,881.52 分毫不差；
金额口径＝发出−收入，与总账借方同向（盘盈在收入侧故显示为负，与底稿写法相同）。
流水表里没有的单据（如资产处置 PRODIS 不走存货流水）**如实标注"仅凭证级"**，不假装有明细。

**教训**：
· **不要用"两个锚点之间全替换"的方式改代码**——中间有什么全凭记忆，而记忆会漏。
· **容错要分类**：外部故障可以软失败，代码错误必须硬失败。一刀切的 `except Exception`
  会把"我把函数删了"伪装成"金蝶不给数"。
· 单测只覆盖算法是不够的，**模块间的接口面也要有测试**。
